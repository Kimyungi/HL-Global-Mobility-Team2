## 1. 구현한 것

### 1.1 차선 인식 파이프라인 (`stack_lane/` 패키지)

```
OAK-D Pro 카메라
  → YOLOPv2 추론 (yolopv2_infer.py)
  → BEV 워프 (bev.py) — 호모그래피는 config/homography.json 있으면 실측, 없으면 카메라 스펙 기반 placeholder
  → 슬라이딩 윈도우 + 중심선 추정 (lane_fit.py)
  → lookahead(3m) 지점 {x,y,yaw,curvature} + confidence (lane_path.py)
  → /perception/lane_path 발행 (node.py)
```

| 모듈 | 역할 |
|---|---|
| `yolopv2_infer.py` | YOLOPv2 TorchScript 추론 (원저자 공식 전처리/후처리 이식) |
| `bev.py` | 호모그래피 로드(실측/placeholder 자동 전환), world↔BEV픽셀 변환 |
| `lane_fit.py` | 다중 후보 탐색(가시거리부터 시작) → 폭(3.7m)+곡률 일치성 검증 → 편측 폴백 → 과속방지턱 등 수직 마킹 필터 |
| `lane_path.py` | 다점(20개) 경로 산출 + REF_POINT_00 근거리 치환 + confidence 스코어링 + 프레임 간 연속성 체크 |
| `debug_draw.py` | 디버그 시각화(오버레이+BEV+ref_point 투영) — node.py와 tools 공용 |
| `logging_utils.py` | CSV 프레임 로거 |
| `node.py` | 실제 ROS2 노드 — 카메라 구동, 파라미터화, `/perception/lane_path` 발행, 선택적 디버그 이미지/CSV 로깅 |

### 1.2 개발 도구 (`tools/`)

- `benchmark_pipeline.py` — 전체 파이프라인 프레임당 소요시간 측정

### 1.3 통합 테스트용 스크립트 (`scripts/`)

- `dummy_estop_clear.py` — stack_estop 미연결 상태에서 통합 테스트하기 위한 테스트 전용 더미 (실제 장애물 감지 없음, 물리 E-stop 필수 병행)

### 1.4 `adas_mgm` 안전 수정

- **lane_path / gps_path 신선도 watchdog 추가** (`mgm_node.cpp`) — estop과 동일한 패턴. 현재 state가 LANE인데 lane_path가 500ms 이상 안 오거나, WAYPOINT인데 gps_path가 500ms 이상 안 오면 자동으로 estop 강제 → v_ref=0. 기존엔 이 watchdog이 없어서 인지 노드가 죽어도 MGM이 마지막 값을 계속 재사용해 주행을 계속하는 실질적 안전 문제가 있었음 (실차 테스트로 재현·확인 후 수정).

## 3. 실차 CAN 통신 확인 (bridge_dspace)

- **PCAN 자동 연결**: `can-iface@can0.service`가 이미 설치·활성화돼 있어 PCAN 연결 시 자동으로 1Mbps up (추가 조치 불필요)
- **RX(dSPACE→PC)**: `0x200~0x202` 10ms 주기로 정상 수신, 값도 정상 디코딩됨
- **TX(PC→dSPACE)**: `0x101`+`0x100` 정상 송신, counter 증가·v_ref 값 정상 반영 확인
- **왕복 확인**: dummy_ref_publisher(v_ref=0.3)로 실제 차량 속도가 0.3m/s 근처까지 따라 올라가는 것 확인 (종방향 정상)

## 4. 실차 주행 테스트 — 카메라 단독 (2026-08-07, 최초)

물리 E-stop 대기 상태에서 초저속(v_base=0.15) + 완화된 lane_conf 임계값(exit=0.15, return=0.25)으로 진행.

- **종방향(속도)은 정상 작동** — MGM이 카메라 confidence 기반으로 lane/waypoint 전이하며 v_ref를 정상적으로 냄

## 5. 조향 미반응 진단 — 원인 규명 및 해결 (2026-08-08)

### 5.1 초기 가설과 기각 (2026-08-07)

`/adas/target_ref`(우리가 보내는 목표)와 CAN `0x202`(dSPACE 실측 조향각 `str`)을 직접 비교하는 방식으로 좁혀갔다. GPS는 실제로 조향에 성공한 전례가 있어(릴리즈 `gps-bags-20260807`, ±28° 정상 반응 확인), GPS 성공 조건을 하나씩 재현하며 우리 조건과 비교했다.

| 가설 | 테스트 방법 | 결과 |
|---|---|---|
| MGM이 waypoint에 갇혀 lane 값이 전달 안 됨 | target_ref에 `state` 필드 추가 로깅 | state는 대부분 lane 유지, 기각 |
| `/vehicle/vector` 피드백 부재가 원인 | 코드 확인(grep) | stack_lane·MGM 둘 다 애초에 구독 안 함 — 설계상 불필요, 기각 |
| y 부호 규약(좌+/우+) 불일치 | GPS 사례 대조 | GPS도 동일 규약으로 이미 성공 사례 있음, 원인이라 해도 "방향"이지 "무반응"과 별개 |
| state=lane 분기 자체가 dSPACE에 미구현 | CAN 직접 발행 테스트(MGM 우회, state 0 vs 1) | 두 경우 다 무반응 → **이후 state=0도 jitter만 있으면 반응함이 재확인돼 최종 기각** |
| v_ref=0(정지)이라 조향 로직이 트리거 안 됨 | v_ref 0 vs 0.1로 재테스트 | 무반응 동일, 기각 |
| n_points=1이라 궤적 생성에 부족 | 점 1개 vs 2개로 재테스트 | 무반응 동일 → **최종적으론 다점(20개) 자체가 필요조건으로 재확인됨** |
| 발행 주기(20Hz)가 30ms watchdog보다 느려 홀드 모드에 갇힘 | 100Hz로 재테스트 | 무반응 동일, 기각 |

### 5.2 돌파구: GPS bag 재생 vs 정적값 발행 대조 (2026-08-08)

GPS의 실제 성공 bag(`gps-bags-20260807`)을 그대로 재생하니 **str이 실제로 ±56.7° 반응**했다. 반면 동일한 state/v_ref/점개수를 정적으로(매 프레임 완전히 같은 값) 발행하면 무반응이 재현됐다. 차이를 좁혀가며 다음을 발견:

- **매 CAN 프레임(10ms)이 직전 프레임과 완전히 동일하면 dSPACE가 이를 "죽은 신호"로 판단해 무시하는 것으로 보임.** 목표 y에 작은 sine 흔들림(jitter)만 넣어도(`scripts/static_multi_point_publisher.py`) str이 반응하기 시작(24.6°~45° 확인).
- **REF_POINT_00(첫 점)만 실제 조향 계산에 쓰임.** `stack_avoid/avoid_to_ref.py:97` 주석("dSPACE는 REF_POINT_00만 디코딩")과 GPS의 `ref_lookahead_m` 튜닝 이력(`docs/dspace_steering_tuning_20260803.md`)이 동일 결론을 이미 실측으로 확인해둔 상태였음. 게인은 pure-pursuit 근사 κ≈2y/(x²+y²)를 따라 REF_POINT_00 거리(x)가 가까울수록 커짐.
- **나머지 19개 점은 "메시지가 유효하다"는 판정(다점 지평 요구)에 쓰이는 것으로 보이나, 곡률 계산 자체엔 관여하지 않음.**

### 5.3 근본 원인: 우리 쪽 갱신 속도(~21Hz) vs CAN 주기(100Hz) 불일치

stack_lane의 실측 프레임 주기는 평균 45ms(≈21Hz)인데 MGM은 10ms(100Hz)마다 CAN을 쏜다. 기존 MGM 조립 블록(`adas_mgm/core/mgm_step.cpp`의 `assemble()`)은 새 인지값이 안 오면 직전 값을 그대로 반복 발행했다 — 실측 결과 **CAN 프레임의 78.7%가 직전 프레임과 완전히 동일**했다. §5.2의 발견과 결합하면, 이게 dSPACE가 우리 신호를 "죽었다"고 보는 직접적 원인이었다.

### 5.4 해결책

1. **MGM 조립 블록에 차량 이동 보정(motion compensation) 추가** (`adas_mgm/core/mgm_step.cpp`/`mgm_types.hpp`) — 인지 소스가 직전 틱과 완전히 같은 값을 낼 때, 그 값을 그대로 반복하지 않고 `x -= st.v × 10ms`로 전방 거리만 깎아서 내보낸다. 실제 속도 피드백(dSPACE 0x202) 배선 없이 직전 틱에 명령한 속도(`st.v`)를 등속 근사로 사용. 검증: 동일 실카메라 로그 재생 시 중복 프레임 비율이 78.7% → **0%**로 떨어짐(`sim_replay.cpp`, 오프라인 시뮬레이션).
2. **REF_POINT_00 근거리 치환** (`lane_path.py`의 `ref_point0_lookahead_m`/`ref_point0_extrap_mode`/`ref_point0_min_confidence`) — 카메라 최소 가시거리(2.5m)로 정해져 있던 REF_POINT_00을 더 가까운 지점(예: 1.5~2.0m)으로 옮겨 pure-pursuit 게인을 높임. 실측 근거 없는 구간이라 접선(linear) 외삽 + confidence 게이팅으로 리스크를 낮춤. **A(2.5m)/B(quad 2.0m)/C(linear 2.0m)/D(linear 1.5m) 비교 실주행에서 D가 가장 뚜렷한 지연 있는 정상 추종 패턴을 보임** (target_y 상승→str 0.4~0.8초 지연 후 반응→함께 원점 복귀).

### 5.5 잔여 이슈: 게인·리셋에 따른 오실레이션

REF_POINT_00을 가까이 당길수록(게인↑) 카메라 프레임 간 자연 노이즈(±0.05~0.1m)도 함께 증폭돼 저주파(수~수십 초 주기) 흔들림이 커지는 경향 확인 (GPS 팀이 과거 겪은 위빙과 동일 메커니즘 — 그쪽은 반대로 lookahead를 늘려 해결). 1.5m→1.7m→2.0m 순으로 실주행 비교 중이며, 2.0m가 현재까지 가장 안정적. 별도로 §6.4의 "연속성 체크 리셋 시 y가 한 번에 2~3m씩 튀는" 부작용도 오실레이션 체감을 키운 것으로 확인 — `y_jump_reset_after` 도달 시 무조건 수용하는 대신 허용폭을 점진적으로 넓히는 방식으로 개선 필요(미착수).

### 5.6 남은 팀 확인 필요 사항 (손상민)

- `0x202`의 `counter` 필드가 모든 관측 세션에서 0 고정 — 프로토콜상 채우기로 했으면 반영 필요 (조향 자체는 살아있는 신호에 반응하는 게 확인됐으니 급하진 않음)
- `str` 부호 규약(PROTOCOL.md는 좌+ 가정) — 재확인 필요
- 다른 스택(GPS RTK 갱신 지연, 회피 등)도 인지 갱신 속도가 CAN 주기보다 느려질 수 있어 동일한 "정지신호 무시" 이슈에 잠재적으로 노출됨 — §5.3/5.4 발견 공유 필요

## 6. 차선 인식 견고성 개선 (2026-08-08)

### 6.1 슬라이딩 윈도우 사각지대 낭비

`_climb_windows()`가 이미지 맨 아래(x=0m, 차 바로 앞)부터 클라이밍을 시작해, 카메라 사각지대(0~2.5m)에 해당하는 윈도우가 9개 중 3개꼴로 항상 빈 채 낭비되고 있었다(구조적으로 hit_ratio 최대치가 0.67로 제한). `visible_x_min_m` 파라미터로 클라이밍 시작점을 실제 가시거리(2.5m)로 옮김 — 합성 테스트에서 hit_ratio 0.667(한계) → **1.0**으로 개선 확인.

### 6.2 연석 오검출 (곡률 불일치)

실주행에서 진짜 왼쪽 차선(c2=-0.004, 거의 직선)과 도로 연석(c2=-0.516, 코너를 따라 급격히 휘는 곡선)이 우연히 폭 조건(3.7±0.6m)을 통과해 "both"로 잘못 짝지어짐 → 중심선 yaw가 58°까지 폭주 → 안전장치가 정지시킴. `fit_lane()`의 폭 검증에 **좌우 곡률(c2) 일치성 검사(`max_c2_diff=0.15`)**를 추가 — 진짜 평행한 차선 쌍은 곡률이 비슷하고 연석처럼 한쪽만 급격히 휘면 크게 어긋나는 성질을 이용. 합성 재현 테스트로 검증(오검출 쌍 기각 → 좋은 쪽만 편측으로 살아남음, hit_ratio 0.889).

### 6.3 yaw 절대각도 클램프 제거

곡률 불일치 검사 도입 전엔 최종 경로점의 |yaw|>20°면 'none' 처리했으나, 실제 코스에 S자/ㄱ자(반경 1.4~2.6m)가 있어 **진짜 급커브도 근거리 점에서 yaw 60°대가 나올 수 있음**(연석 오검출 사례 58°와 크기가 겹쳐 절대각도로 구분 불가). "both" 모드는 §6.2의 상대 비교로 대체, 편측(한쪽만 검출) 모드는 비교 대상이 없어 각도 검사를 아예 제거하고 검출 품질(hit_ratio 기반 confidence)에만 의존하도록 변경. y(횡오프셋) 절대값 검사는 유지하되 2.5m→**4.0m**로 완화(편측 폴백의 차선폭 오프셋 계산이 정상 검출임에도 경계를 근소하게 넘겨 전체 프레임이 폐기되던 버그 수정).

### 6.4 프레임 간 연속성 체크

`fit_lane()`은 매 프레임 후보를 처음부터 새로 찾아 직전 프레임 기억이 없다 — 검출이 애매한 순간 모드가 짧은 시간에 여러 번 바뀌다가(실측: 3초 사이 6회 이상) 엉뚱한 선에 고정되며 y가 갑자기 2m 이상 튀는 사례 확인(예: y=-2.58m로 고정돼 9초 이상 유지, 차량이 한쪽으로 치우쳐 주행). `estimate_lane_path()`에 `prev_y`/`max_y_jump_m`(기본 1.0m) 파라미터를 추가해 직전 채택값 대비 과도한 점프를 거부. 단, `y_jump_reset_after`(연속 거부 한계) 도달 시 무조건 수용하는 현재 방식이 도리어 순간적인 큰 점프를 만드는 부작용 확인 — §5.5 참조, 개선 필요.

### 6.5 알려진 한계 — 교차로/횡단보도

교차로(횡단보도·정지선·방향 화살표가 뒤섞인 구간)에서 좌우 평행선을 전제로 한 슬라이딩 윈도우가 구조적으로 잘 동작하지 않음(실측: 70초 이상 연속 미검출). GPS·정지선 인식(stack_traffic) 없이 카메라 단독으로는 완전한 해결이 어려움 — 팀 설계상(CLAUDE.md §6) 교차로/정지 판단은 stack_traffic 몫이라, 카메라 단독 테스트에서의 정지는 예상된 동작에 가까움. 최소한 "장시간 미검출 시 정지 대신 직전 방향 유지" 정도의 완화는 추후 검토 가치 있음.

### 6.6 다항식 계수 EMA 저역통과 필터 (오실레이션 완화, 2026-08-08)

§5.5에서 확인한 오실레이션(REF_POINT_00을 가깝게 당길수록 프레임 간 미세 흔들림 ~0.05~0.1m까지 증폭)에 대한 대응. §6.4의 연속성 체크는 "엉뚱한 값"만 거를 뿐 정상 범위 내 흔들림은 못 잡는다는 한계가 있어, GPS(`stack_gps`)의 `fusion_alpha`(헤딩 융합 저역통과, 커밋 `1129604`)와 동일 기법을 다항식 계수(c2/c1/c0)에 적용:

```
smoothed = alpha * 이번_프레임_계수 + (1 - alpha) * 직전_smoothed_계수
```

**설계상 중요한 순서**: 이상치 검사(연속성/타당성)는 반드시 원본(raw) 계수로 먼저 수행하고, 통과한 것만 스무딩한다. 순서를 반대로 하면 큰 튐이 스무딩을 통해 여러 프레임에 걸쳐 서서히 섞여 들어가 연속성 체크가 아예 못 잡게 되는 부작용이 생김 — 단위 테스트로 이 인터랙션을 검증(§코드 `lane_path.py::estimate_lane_path` docstring 참조).

새 파라미터 `coeff_smoothing_alpha`(기본 1.0=비활성). 실주행 검증(REF_POINT_00=1.5m linear, alpha=0.3):
- str 변동폭 45° → **20°**로 감소
- target_y와의 상관계수 -0.10~-0.35 → **-0.54**로 개선
- 세부 구간 대조 결과, 남은 흔들림 대부분이 자려진동이 아니라 실제 목표 변화를 0.25~0.5초 지연으로 따라가는 정상 추종으로 확인됨

### 6.7 목표 주행 속도(4~8km/h) 상향 계획

현재 검증은 전부 v_base=0.5m/s(1.8km/h, 도보보다 느림)에서 진행됨. 목표인 4~8km/h(1.1~2.2m/s)로 올리면:
- 카메라 가시 구간(2.5~6.0m 고정)을 통과하는 시간이 비례해서 줄어 반응 여유가 줄어듦
- 스무딩 필터의 시간 지연이 그대로 거리 지연으로 변환돼 커짐(예: 150ms 지연 → 0.5m/s에서 7.5cm, 2.0m/s에서 30cm)

**제안된 방향(미구현)**: pure-pursuit 표준 기법대로 REF_POINT_00 lookahead를 속도에 비례(`k × v_ref`)하게 만들어 저속/고속에서 일관된 반응성 유지. `coeff_smoothing_alpha`도 속도별 재튜닝 필요할 가능성 있음. 단계적으로(0.5→1.0→...m/s) 검증 예정.

## 7. 오실레이션 정밀 진단 및 리셋 로직 재설계 (2026-08-10)

### 7.1 3계층(카메라 인식/ADAS MGM 천이/Vehicle MGM 추종) 구분 로깅

오실레이션 원인이 세 계층 중 어디인지 로그만으로 구분할 수 있도록 필드 추가:

- `lane_*.csv`: `reject_reason`(`no_fit`/`implausible`/`discontinuous`/`held`/`search`) — 'none'이 **진짜 검출 실패**인지 **우리 필터가 거부**한 건지 구분
- `steering_*.csv`(`log_steering_correlation.py`): `target_x_m`(REF_POINT_00의 실제 x) 추가 — 기존엔 y만 남겨서 pure-pursuit 이론 곡률(κ=2y/(x²+y²))과 실측 str을 대조할 방법이 없었음

**진단 결과**: 1.5m lookahead 테스트에서 none의 89%가 진짜 검출 실패(no_fit)였는데, 1.0m lookahead 테스트에서는 none의 76%가 우리 연속성 체크(discontinuous)의 자체 개입이었음 — **거리를 좁힐수록 우리 필터 스스로가 더 자주 개입하게 되는 경향 확인**(원인은 다른 주행 조건 때문일 수도, 강한 게인의 피드백 루프 때문일 수도 있어 추가 확인 필요).

또한 target_y가 5.4초간 거의 완전히 고정된 구간에서 str도 같이 안정적임을 확인(변동폭 0.3°) — **Vehicle MGM(dSPACE) 자체의 자려진동은 아님**을 실측으로 배제. 다만 리셋 버그로 생긴 극단값(예: y=-2.97m)에 str이 반응하기도/안 하기도 해 일관성이 낮았음 — 이게 §7.2로 이어짐.

### 7.2 HELD→SEARCH→LOST 점진적 신뢰도 감쇠 (리셋 버그 수정)

기존 `y_jump_reset_after`(고정 프레임 후 무조건 통과) 방식이 리셋 순간 검사 없이 큰 튐(3.1m)을 그대로 받아들여 str이 -18~-20°까지 흔들리는 사례를 실측 확인(§7.1). `YOLOPv2_PC_LANE_CORRIDOR` 참조 프로젝트의 `LaneTrajectoryTracker` 상태머신을 이식:

```
VALID → (검출 실패) → HELD(hold_frames=12, ~0.6s, confidence를 매 프레임 0.65배 감쇠)
      → SEARCH(search_frames=30, ~1.5s, confidence 바닥 유지 + 연속성 체크 허용폭을 서서히 최대 3배까지 확대)
      → LOST(완전 리셋, 다음 정상 검출은 검사 없이 즉시 수용)
```

급격한 단일 리셋 지점이 사라짐 — 시뮬레이션으로 상태 전이·confidence 감쇠 곡선·LOST 이후 정상 복귀 전부 검증 완료. 실차 검증은 진행 중(§7.3).

### 7.3 오실레이션 정량 분석 — 잔차 부호전환 주기 + FFT

str의 절대 표준편차만으론 "정상 조향(커브)"과 "진짜 오실레이션"을 구분 못 해 — 이동평균(2초 창) 대비 잔차로 재정의 후 부호전환 주기·FFT 지배주파수를 계산하는 방식 도입.

REF_POINT_00 거리별(1.5m/1.8m/2.5m 비활성) 비교 결과:

| 거리 | str std | 잔차 std | FFT 지배 주기 |
|---|---|---|---|
| 1.5m | 6.80° | 2.10° | 2.41s |
| 1.8m | 5.70°(최저) | 1.92°(최저) | 2.24s |
| 2.5m(비활성) | 7.61° | 2.17° | 2.51s |

**세 설정 모두에서 약 2.2~2.5초 주기의 진동이 공통으로 관측됨** — 거리를 바꿔도 이 주기 자체는 거의 안 변함. REF_POINT_00 튜닝으로 없앨 수 있는 종류가 아니라 **제어 루프에 내재된 고정 주기 성분일 가능성** — GPS 팀이 이미 dSPACE에 요청했던 "MPC 예측 모델에 조향 액추에이터 지연 반영" 요청과 같은 계열의 문제로 추정, 손상민 확인 필요(§7.4). 1.8m는 표본이 51초뿐이라 재현성 확인을 위한 장시간(5분+) 재테스트 필요.

### 7.4 `/vehicle/vector` 관련 — 사용 보류

MGM 이동보정(§5.4)을 실측 v로, 오실레이션 판정을 실측 vehicle yaw로 개선하려 했으나, **`/vehicle/vector`(0x200/0x201)가 dSPACE에서 실제로 갱신되는 값인지 미확인 상태**(우리 로그가 지금까지 0x202만 파싱해왔어서 직접 검증한 적 없음, `counter` 0 고정과 같은 종류의 미구현 가능성). 검증 전까지는 이 피드백에 의존하는 개선은 보류하고, str 자기 자신의 시계열(이동평균 잔차 방식, §7.3)로 오실레이션을 판정하는 쪽으로 전환.
