# MGM 상태 머신 변경 메모

기록일: 2026-09-16

현재 진행 중인 상태 머신 요구사항 인터뷰의 지속 메모다.
**기존 상태 머신 코드를 수정하지 않고, 원하는 전이 조건과 현재 구현의 차이만 정리한다.**
이 파일은 인터뷰 전체 답변의 최종 보고서가 아니며, 사용자가 지속 기록을 요청한
ESTOP 관련 질문 66·67번을 우선 보존한다.

## 질문 66 — 독립 E-stop 삭제 후 ESTOP 상태 추가 예정

사용자 요청:

> 독립 estop 삭제 후 estop스테이트 추가할 것을 코멘트로 남겨서 estop과 관련된 일을 할 때 말해줘.

- 독립 `stack_estop`의 정지 요청을 소비하는 기존 방식을 사용하지 않을 예정이다.
- 독립 E-stop을 삭제하고 상위 제어의 **ESTOP 상태 블록**에서 진입·해제를 판단하는 방향이다.
- 기존 `SafetyState::AUTO_ESTOP` 구현을 새 ESTOP 상태가 이미 구현된 것으로 설명하지 않는다.
- 이후 ESTOP 관련 작업 시 이 변경 예정 사항을 사용자에게 먼저 알린다.
- 앞서 질문 9에서 유지하기로 한 독립 E-stop 메시지 신선도 0.25초 검사는
  해당 입력을 없애는 설계에 맞춰 재검토해야 한다. 새 입력의 신선도 기준은 미정이다.

## 질문 67 — 반영할 전이 조건

| 구분 | 사용자 요구 |
| --- | --- |
| 진입 | 전방·좌측·우측 LiDAR에서 설정 거리 안의 물체를 감지하면 ESTOP 상태로 전환 |
| 종료 | 고정된 회복주행을 완료하면 ESTOP 상태를 탈출 |
| 내부 동작 구상 | 해당 상태 안에서 후진 등 주행 복귀를 위한 동작 수행 |
| 이번 인터뷰 범위 | 진입·종료 조건만 요구사항에 반영. 내부 회복주행 로직은 기억만 하고 구현하지 않음 |

현재 구현과의 차이:

- 현재 MGM은 독립 E-stop 모듈에서 받은 실제 정지 요청을 Safety 판단에 사용한다.
  새 요구사항은 상위 제어가 LiDAR 장애물 정보에 따라 ESTOP 진입을 판단하는 것이다.
- 현재의 일반 E-stop 해제와 별도 후진 탈출 조건을 새 설계의 종료 조건으로
  그대로 가져오지 않는다. 새 설계의 종료 기준은 **고정 회복주행 완료**다.
- 단순 장애물 소실만으로 새 ESTOP을 종료한다고 가정하지 않는다.
- 후진을 포함할 수 있지만, 구체적인 순서·거리·속도·시간은 아직 결정하지 않았다.

## 질문 68 — 회복주행 완료 후 복귀 상태

- 사용자 선택: **1번, ESTOP 진입 직전의 주행 상태로 복귀**.
- 진입 당시 주행 상태를 기억하고, 고정 회복주행이 완료되면 해당 상태로 돌아간다.
- 회복 완료 시점의 조건으로 새로운 주행 상태를 재선택하는 방식은 선택하지 않았다.
- 이번에는 전이 요구사항만 기록하며 상태 저장·복귀 코드는 구현하지 않는다.

## 질문 69 — 주차 중 ESTOP 진입

- 사용자 결정: **PARKING 중에도 ESTOP 진입 허용**.
- 전방·좌측·우측 LiDAR의 설정 거리 조건이 성립하면 PARKING에서 ESTOP으로 전환한다.
- 질문 68의 복귀 규칙에 따라, 고정 회복주행 완료 후 PARKING으로 복귀한다.
- 현재의 PARKING 중 독립 LiDAR E-stop 억제와 달라지는 요구사항이다.
- 주차 내부 동작의 중단·재개 방법과 ESTOP 회복주행 구현은 이번 결정에 포함하지 않는다.

## 질문 70 — 신호 정차 중 ESTOP 상황

- 사용자 답변: **신호를 기다리며 멈춰 있으면 ESTOP이 걸릴 이유가 없음**.
- 해당 상황은 운용상 고려하지 않는 것으로 기록하고, 별도의 예외 전이 요구사항을 추가하지 않는다.
- 이 답변을 신호 정차 중 센서 검출을 무시하거나 ESTOP 진입을 강제로 금지하라는
  구현 지시로 확대 해석하지 않는다.

## 질문 71 — ESTOP 진입 연속 확인

- 사용자 선택: **2번, 여러 관측에서 거리 조건이 연속으로 성립한 뒤 ESTOP 진입**.
- 한 번의 검출만으로 즉시 진입하는 방식은 선택하지 않았다.
- 연속 확인 횟수는 질문 72에서 3회, 집계 방식은 질문 73에서 센서별 확인으로 확정했다.

## 질문 72 — ESTOP 진입 확인 횟수

- 사용자 결정: **설정 거리 내 물체 감지를 3회 연속 확인한 뒤 ESTOP 진입**.
- 설명 기준: 현재 LiDAR 설정은 센서당 10Hz다. 한 센서의 새 스캔 3회라면
  첫 검출부터 약 0.2초, 감지 범위 진입부터 약 0.2~0.3초에 해당한다.
  이는 일정한 10Hz를 가정한 설명이며 통신·처리 지연은 별도다.
- 고정 시간 0.3초로 결정한 것이 아니라 **관측 3회**로 결정했다.
- 질의 당시 LiDAR 드라이버와 스캔 토픽은 실행 중이지 않아 실시간 수신율은 측정하지 않았다.

## 질문 73 — 센서별 연속 검출

- 사용자 결정: **한 센서에서 3회 연속 감지**.
- 전방·좌측·우측 LiDAR별로 연속 확인하며, 그중 어느 한 센서의 거리 조건이
  3회 연속 성립하면 ESTOP 진입 조건을 충족한다.
- 서로 다른 센서의 검출 횟수를 합쳐 3회로 인정하지 않는다.

## 질문 74 — 장애물 거리 기준

- 사용자 결정: **차체 외곽 기준**.
- 전방은 앞범퍼, 좌·우측은 해당 차체 옆면에서 물체까지의 여유 거리를 사용한다.
- LiDAR 센서 원점에서 측정한 거리를 그대로 ESTOP 거리 문턱으로 사용하는 방식은 아니다.
- 센서 장착 위치를 반영하는 구체적인 거리 계산 구현은 수행하지 않았다.

## 질문 75 — 전방 ESTOP 진입 거리

- 사용자 결정: **앞범퍼에서 물체까지 0.25m 이내**.
- 전방 LiDAR의 해당 거리 조건을 3회 연속 확인하면 ESTOP 진입 조건을 충족한다.
- 요청한 전이 문턱을 기록한 것이며, 이 거리에서 실제 충돌 전 정차 또는 회복주행이
  가능하다는 실측 검증 결과를 의미하지 않는다. 코드·설정은 변경하지 않았다.

## 질문 76·77 — 좌·우측 ESTOP 진입 거리

- 사용자가 좌측·우측을 함께 지정: **각 차체 옆면에서 물체까지 0.15m 이내**.
- 좌측 또는 우측의 해당 센서에서 거리 조건이 3회 연속 성립하면 ESTOP 진입 조건을 충족한다.
- 전방 0.25m, 좌측 0.15m, 우측 0.15m이며, 서로 다른 센서의 검출 횟수는 합산하지 않는다.

## 질문 78 — 센서 입력 무효 시 확인 횟수 유지

- 사용자 선택: **2번, 기존 확인 카운터 유지**.
- 예: 같은 센서에서 거리 조건을 2회 확인한 뒤 입력이 끊기거나 무효가 되어도
  2회를 기억하고, 정상 입력 복구 후 한 번 더 거리 조건이 성립하면 3회로 인정한다.
- 입력 무효 구간에는 확인 횟수를 증가시키거나 초기화하지 않는다.
- 따라서 질문 71·72의 연속 확인은 입력 무효 구간을 건너뛰는 방식이다.
- 정상 관측에서 거리 조건이 성립하지 않는 경우의 처리는 질문 79에서 초기화로 확정했다.

## 질문 79 — 정상 관측에서 거리 조건 해제 시 초기화

- 사용자 선택: **1번, 해당 센서의 확인 카운터를 0으로 초기화**.
- 정상 스캔에서 물체가 없거나 설정 거리 밖이면 기존 감지 횟수를 버리고,
  이후 같은 센서에서 다시 3회 연속 감지해야 ESTOP 진입 조건을 충족한다.
- 입력 무효 시에는 횟수 유지(질문 78), 유효한 관측에서 조건 해제 시에는 초기화로 구분한다.

## 질문 80 — 회복 완료 후 거리 조건 해제를 거쳐 재진입

- 사용자 선택: **2번, 거리 조건 해제 후 재진입 허용**.
- 고정 회복주행을 완료하면 질문 68대로 이전 주행 상태로 복귀한다.
- 물체가 계속 설정 거리 안에 있는 동안에는 같은 조건으로 ESTOP에 반복 진입하지 않는다.
- 정상 관측에서 거리 조건이 한 번 해제된 뒤, 다시 한 센서에서 3회 연속 감지되어야 재진입한다.
- 센서 입력 무효를 거리 조건 해제로 간주하지 않는다.
- 재진입 억제 범위와 다른 방향의 감지는 질문 81에서 센서별 적용으로 확정했다.

## 질문 81 — 재진입 제한은 센서별 적용

- 사용자 선택: **1번, 센서별 제한**.
- 예: 전방 조건으로 ESTOP 회복주행을 완료했는데 전방 물체가 계속 가까이 있으면
  전방 조건의 반복 진입은 억제한다.
- 이때 좌측 또는 우측에서 새로 3회 연속 거리 조건이 성립하면 해당 센서 조건으로
  ESTOP 진입을 허용한다.
- 제한된 센서는 정상 관측에서 자기 거리 조건이 해제된 뒤 새 연속 검출을 시작한다.
- 세 방향이 모두 해제되어야 전체를 재허용하는 방식은 선택하지 않았다.

## 질문 82 — 운전자 정지 최우선

- 사용자 결정: **현재 운전자 정지 우선권 유지**.
- `scripts/v2 stop`은 주차·후진 및 새 ESTOP 회복주행을 포함한 모든 주행 동작보다
  우선하여 즉시 목표속도 0을 요청하고 출발 인가를 해제한다.
- 이후 움직이려면 다시 `go` 인가를 받아야 한다.
- 중단된 ESTOP 회복주행을 재인가 후 어느 내부 단계에서 이어갈지는 구현 보류 범위다.

## 질문 110 — 새 ESTOP 판정에 사용할 LiDAR 데이터 유효 시간

- 사용자 선택: **1번, 마지막 수신 후 0.35초를 초과하면 오래된 데이터로 판단**.
- 전방·좌측·우측 센서별로 적용한다. 출발 준비 기준과 같은 시간을 선택한 것이며,
  현재 독립 E-stop의 기존 유효 시간을 그대로 유지한다는 뜻은 아니다.
- 오래되거나 무효인 입력은 감지 횟수를 증가시키거나 초기화하지 않는다(질문 78).
- 같은 스캔을 반복 처리하여 3회 감지로 세지 않는다. 새 유효 스캔으로 판정한다.
- 요구사항만 기록했으며 코드·설정은 변경하지 않았다.

## 질문 111 — ESTOP 회복주행 중 전체 센서 소실

- 사용자 선택: **2번, 고정된 ESTOP 회복주행을 계속 수행**.
- ESTOP 회복주행 중에는 감시 대상 센서 전체 소실만을 이유로 SAFE_STOP으로
  전환하거나 회복주행을 중단하지 않는다. 일반 주행의 전체 센서 소실 정지 정책은 유지한다.
- 이는 전체 센서 소실에 대한 예외이며, 운전자 정지 우선권(질문 82)을 취소하지 않는다.
- CAN 고장 등 다른 정지 사유까지 무시한다는 뜻으로 확대하지 않는다.
- 회복주행 내부 로직은 계속 구현 보류이며, 코드·설정은 변경하지 않았다.

## 질문 112 — ESTOP 회복주행 중 CAN 고장

- 사용자 선택: **1번, CAN 고장에 의한 정지를 우선 적용**.
- ESTOP 회복주행 중에도 앞서 유지한 CAN 고장 감지 조건이 성립하면
  목표 속도 0을 요청하고 회복주행을 중단한다.
- 질문 111의 전체 센서 소실 예외를 CAN 고장에는 적용하지 않는다.
- 정지 명령의 실제 차량 전달 성공을 보장한다는 의미는 아니다.
- 중단 후 회복주행 내부 단계의 재개 방식은 구현 보류 범위다.
- 요구사항만 기록했으며 코드·설정은 변경하지 않았다.

## 추가 확인이 필요한 전이 명세

- PARKING 외 상태에서의 진입 및 다른 정지 요청의 우선순위.
- 세션 종료 시의 상태 처리. 운전자 정지의 출력 우선권은 질문 82,
  ESTOP 회복주행 중 전체 센서 소실 시 계속 수행은 질문 111,
  CAN 고장 정지 우선 적용은 질문 112에서 확정.

이 미정 항목들을 기존 코드의 수치나 조건으로 임의 확정하지 않는다.

## 구현 보류 범위

- 회피: 방향성 변경 및 구현 중. 질문 32 이후의 회피 경로 소실·복귀 등 세부 조건 보류.
- 주차: GPS 위주로 변경 중. 질문 61의 구간 진입 시 PARKING 전환은 유지하되
  현재 벽 획득·탐색·제어권 인계·종료 세부 로직은 확정하지 않음.
- ESTOP: 위 진입·종료 요구사항만 기록. 기존 모듈 삭제, 새 상태 추가,
  후진·회복주행 구현은 이번 메모 작업에서 수행하지 않음.

## 2026-09-16 구현 요청 및 추가 확정

인터뷰 종료 후 사용자가 현재 v2 상태 머신을 확정 요구사항에 맞춰 **코드 변경**하고
불일치 동작을 제외해 달라고 명시했다. 따라서 앞부분의 "코드 변경 없이 기록"은
인터뷰 당시의 범위이며, 현재 구현 요청에 대한 금지로 적용하지 않는다.

- 질문 99: 카메라가 정상인 일반 구간은 카메라 주행과 CSV 전환을 병행한다.
- 질문 102: 마지막 경로는 실제 정차를 확인한 뒤 FINISH.
- 질문 103: 경로 끝은 미도착 → 새 도착 관측 순서로 인정.
- 질문 104: FINISH 후 go만으로 재출발하지 않으며 새 prepare 세션 필요.
- 질문 105: 같은 세션 내 CSV 전환은 미션 완료/실패 기록 유지.
- 질문 106: 미션 zone 내부에서 출발은 운용 범위 밖. 새 예외 동작 추가 없음.
- 질문 107·108: 앞선 '연결 구간 GPS 강제 유지'를 최종 답변으로 대체.
  좌·우회전 zone 밖의 CSV 연결 구간에서도 차선 주행 허용.
  낮은 차선 신뢰도로 GPS가 필요한데 FLOAT이면 정지.
  정지 중 FIXED 또는 차선 복구로 별도 go 없이 재출발.
- 질문 109: 위 차선 복구는 신뢰도 ≥0.70을 50회 확인.
- 질문 113: 신호 정지 감속 중 ESTOP은 운용 범위 밖. 검출 무시 조건은 추가하지 않음.
- 구현 중 추가 답변: **회피·주차 모듈 연결을 유지하고 상위 전이 조건만 변경**.
- 지도 추가 답변: **기존 GPS 전용 구간 자동 적용 제외, 새 zone은 추후 설정**.

실행 경로는 `scripts/v2 prepare/drive`의 `revised_v2_enabled=true`다.
독립 E-stop 실행/구독과 기존 자동 후진은 이 경로에서 제외했다.
상위 ESTOP 전이 및 `EstopRecovery` 입력 계약을 추가했지만 내부 회복주행 실행기는
여전히 구현 보류다. 실행 입력이 없으면 목표 0으로 대기한다.
기존 프로파일·로그 재현용 소스 자체는 삭제하지 않았다.
