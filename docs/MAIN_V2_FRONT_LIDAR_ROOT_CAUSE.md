# main / integration/v2_main 전방 장애물 오인 원인 분석

분석일: 2026-09-13. 비교 기준은 `main=c76f287`, 원격 `integration/v2_main=c5b32c8`이다.
이번 방향 수정은 원인 비교에서 제외하고 위 두 커밋의 원본을 사용했다.

## 결론

주원인은 주차 통합 시 **원본 스캔 입력만 교체하고 소비자의 방향 계약을 교체하지 않은 것**이다.
v2에서 새로 만든 결함이 아니라 main에서 물려받은 통합 결함이다.
단일 라이다 모드가 정상이라는 사실은 4-LiDAR 주차 통합 모드의 방향 정합을 보장하지 않는다.

| 구성 | 입력과 드라이버 | E-stop / 회피 해석 | 판단 |
|---|---|---|---|
| main 단일 라이다 | `/scan`, reversion=false | yaw +90도 / raw 전방 270도 | 기존 단일 라이다 계약 유지 |
| main 주차 통합 | `/lidar/a1/scan`, reversion=true | yaw +90도 / raw 전방 270도 | a1 보정 -87도와 불일치 |
| 수정 전 v2 주차 통합 | `/lidar/a1/scan`, reversion=true | yaw +90도 / raw 전방 270도 | main의 결함 유지 |
| 수정본 | 같은 a1 원본 | yaw -87도 / raw 전방 87도 | fusion의 보정 방향과 일치 |

## 발생 이력과 근거

1. 단일 라이다용 통합 런처는 `reversion=false`, `inverted=false`로 구동하고,
   E-stop은 `angle + yaw`, 회피는 `angle - forward_angle`로 방향을 계산한다.
   +90도 yaw와 270도 forward_angle은 같은 방향을 뜻한다.
2. 2026-09-04 [`1b02d15`](https://github.com/Kimyungi/HL-Global-Mobility-Team2/commit/1b02d15a1fd2152baa3efc120df5b521f7c2ddef)의
   `feat(parking): trigger typed parking modes from GPS`가 `parking_enabled=true`일 때
   단일 드라이버를 끄고 주차용 네 드라이버를 켜며, E-stop·회피의 입력을 a1으로 바꿨다.
   이 변경에는 소비자 yaw/forward_angle의 분기가 없었다. `git log -S`와 `git blame`으로 확인했다.
3. main의 주차 드라이버 `multi_lidar_drivers.launch.py`는 이미 `reversion=true`였다.
   SDK `CYdLidar.cpp`의 `m_Reversion` 분기는 실제로 각도에 π를 더한다.
   같은 센서라도 이 설정이 바뀌면 원본 각도를 같은 뜻으로 읽을 수 없다.
4. v2 초기 커밋 `8697bcb`는 이 연결을 물려받았다. 후속 `3c5aa9c`는 주차 드라이버를
   `lidar_fusion_v2/drivers.launch.py`로 바꾸어 a1의 9K/16bit/고정 해상도를
   4K/8bit/가변 해상도로 맞췄지만, 이전과 이후 모두 `reversion=true`, `inverted=false`였다.
   따라서 이 교체는 177도 방향 불일치의 최초 원인이 아니다.
5. main과 v2의 `fixed_geometry.yaml`, `driver_profiles.py`, 회피 설정 YAML은 비교 기준에서 동일하다.
   E-stop 검출 함수와 회피의 방향 계산에도 이 차이를 해소하는 변경이 없었다.

드라이버의 180도 회전과 장착 보정 차이가 결합해, 현재 a1의 올바른 yaw -87도와
기존 소비자의 +90도 사이에는 **177도** 차이가 난다. 이는 `inverted`에 의한 좌우 거울상 문제와 다르다.

## RViz는 정상인데 인지가 틀린 이유

주차/fusion 경로는 a1 원본을 고정 FOV(-3~177도)로 제한한 뒤 -87도 yaw와
장착 위치를 적용해 `/unified_lidar/cloud` 및 `/unified_lidar/scan`을 만든다.
반면 E-stop·회피는 그 보정 출력을 구독하지 않고 a1 원본을 직접 읽는다.
두 소비자는 TF를 조회해 자동 변환하지 않고 각각의 파라미터로 삼각함수를 계산한다.
따라서 보정 점군의 RViz 표시가 맞아도 장애물 판정은 반대쪽을 볼 수 있다.
현장에서 실제로 표시한 RViz 토픽은 원본 기록 없이 확정할 수 없으나, 코드의 두 처리 경로는 확인됐다.

## 커밋 원본을 사용한 재현

두 커밋의 통합 런처, 설정 파일, E-stop·회피 노드를 Git에서 별도 임시 디렉터리로 읽었다.
실제 런처 파라미터를 평가하고 각 커밋의 검출 함수를 호출했다. ROS 노드/차량은 실행하지 않았다.

| 합성 a1 입력(각도 간격 1도, 5점, 거리 0.6m) | main 결과 | 수정 전 v2 결과 |
|---|---|---|
| raw -93도 중심: 차량 뒤쪽 | E-stop·회피 모두 전방 약 0.597717m 검출 | 동일 |
| raw +87도 중심: 차량 전방 | 두 소비자 모두 전방 장애물 미검출 | 동일 |

단일 라이다 계약의 raw -90도 전방 군집은 두 커밋 모두 검출했다.
즉 알고리즘 전체가 무작위로 고장 난 것이 아니라 입력 좌표 계약을 잘못 연결한 것이다.
실제 오인 반사점이 차체/케이블/뒤쪽 물체 중 무엇인지는 rosbag 원본이 없어 확정하지 않았다.

## 저속 회피 증상은 별도 구분

E-stop만 제외하면 같은 잘못된 a1 해석을 하는 회피 노드는 여전히 장애물을 보고할 수 있다.
main의 기존 MGM에는 `v_avoid=0.6`, `v_narrow=0.2` 제한이 있어, 회피가 활성인 버전이라면
오인 장애물과 결합해 저속 회피가 나오는 경로가 존재한다.

하지만 현재 v2는 기본 `avoidance_enabled=false`이고 비정지 속도도 v_base로 고정한다.
보관된 `v2_no_estop_20260912_223321_282247/session.json` 역시 회피 OFF를 명시한다.
해당 `transitions.csv`의 76개 행은 모두 `avoidance=0`이다.
그 로그는 `8697bcb` 위 미커밋 변경으로 실행됐다고 기록돼 있어 현 HEAD와도 동일하지 않다.
따라서 사용자가 겪은 저속 회피의 실행 시점/바이너리/파라미터는 추가 대조가 필요하다.
그 증상까지 현재 v2 기본 설정에서 확정 재현했다고 말할 근거는 없다.

## 원인 우선순위

- **확정:** a1 입력 전환 시 E-stop·회피의 방향 설정 누락. 두 브랜치 원본으로 재현.
- **구조적 원인:** fusion 보정과 원본 소비자 보정의 기준이 나뉘고, 소비자들이 TF/frame을 검증하지 않음.
- **검증 공백:** 기존 E-stop 테스트는 raw -90도 가정만 검사했고, v2 드라이버 시험은
  통신 프로필·토픽을 검사했지만 실제 a1 방향과 소비자의 전방 판정을 함께 검사하지 않았음.
- **별도 문제:** main a1의 9K/16bit 프로필은 v2에서 수정된 스트림 문제. 방향 불일치와 분리해야 함.
- **미확정:** 실차에서 오인된 반사점의 물체, 저속 회피 당시 실행본/설정, 추가 센서 노이즈의 기여.
