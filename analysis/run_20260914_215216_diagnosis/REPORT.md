## 원인과 남은 정보

1. 최적화는 식을 보존하므로 기존 기하 조건에서 탈락한 후보를 통과시키지 않는다. 이번에도 전체 후보가 탈락하는 상태가 유지됐다. 이것이 유효 회피점 부재의 직접 원인이다.
2. 실제 장면 계산이 여전히 수백 ms~1초로 느리다. 같은 on_scan 콜백 안에서 계산을 마친 뒤 상태를 발행하므로 감지 갱신도 늦어진다. watchdog에 의한 obstacle_detected=false를 실제 장애물 소실과 혼동하면 안 된다.
3. native 시제품이 실제 계산 시간을 개선해도 경로 부재는 별개라 실패 증상이 남을 수 있다. 속도 최적화만으로 이번 문제를 해결하지 못했다.
4. 현재 진단은 후보 없음, 회전반경 초과, entry/exit 충돌, 복귀점 부족을 하나의 실패 문구로 묶는다. 저장된 세션에는 원시 LaserScan/전체 waypoint window와 후보별 탈락 사유가 없다. 어느 조건이 실제 모든 후보를 탈락시켰는지는 확정할 수 없다.
5. 수동 후진 후의 대기 해제는 현재 direct GPS return 분기가 waypoint 정렬에 따라 done을 만들 수 있음을 보여준다. 장애물 뒤를 통과했다는 증명은 아니다. 자동 회피 성공으로 집계해서는 안 된다.

다음 확인에 필요한 기록은 계산 stage별 시간, 후보 개수, 각 후보의 곡률/진입 충돌/복귀 충돌/복귀점 범위 탈락 사유, 그 계산이 사용한 scan·GPS pose·waypoint window다. 이 기록으로 같은 실패 입력을 오프라인 재현한 뒤 수식 보존 범위에서 원인을 좁혀야 한다. 이번 턴에서는 기록 분석만 수행했다.
