적용 모드 `main_gap_path`, native, v_base=2.0, v_avoid=2.0.
주행 코드 변경이나 실차 재기동 없이 분석했다. 6,466 snapshot의 ABI를 확인하고
현재 MGM 코어로 재생했다. 저장된 전이 로그의 top/nav/avoid/safety/ref_valid와
모두 일치하며 속도 명령 최대 수치 차이는 1.2e-8이다.

## 차량 좌표계 가정의 문제 — 강한 의심 근거

새 시제품은 `main_gap_path_trial.py:on_vehicle_vector`에서 수신한 x/y/yaw를
동일한 평면 위치·헤딩으로 간주해 경로를 고정한다. 실제 로그는 이 가정과 맞지 않는다.

22:40:47.296 → 47.776:

- x: 10.1391 → 10.9542, Δx=0.8151m
- y: 10.1453 → 10.9599, Δy=0.8146m
- 위치 변화가 가리키는 방향: 약 44.98°
- yaw: 18.63° → 20.61°
- x/y 변화의 길이: 1.152m; 같은 구간 측정 속도의 적분: 약 0.867m
- 시작 yaw로 환산한 국소 이동: 전방 1.033m, 측방 0.511m

yaw와 x/y를 같은 프레임으로 취급하면 차량이 왼쪽으로 크게 이동한 것으로
보정된다. 실제 MGM의 경로 추종점 y도 약 0.133→0.041→0.022m로 빠르게 작아졌다.
이 좌표 가정은 경로/현재 스캔 정합과 이후 0.5m 이탈 판정을 왜곡할 가능성이 크다.
이번에 추가한 어댑터가 실제 차량 위치 값의 의미를 확인하지 않고 사용한 한계다.
합성 시험은 일관된 x/y/yaw를 제공했으므로 이 실제 입력 불일치를 검출하지 못했다.

다만 이 로그만으로 dSPACE 내부 x/y 필드의 본래 의미나, 최초 충돌 검사를 실패시킨
정확한 빔/장애물을 확정할 수 없다. 원시 스캔과 프레임별 경로가 기록되지 않았다.
좌표 불일치와 실제 차량의 추종 오차/새 장애물 관측을 분리해야 한다.

## 계산 지연·GPS 소실과 구분

해당 진입 구간 AvoidStatus 갱신은 약 90~110ms 주기를 유지한다. 최초 무효화 당시
직전 reference age는 0.211초로 0.5초 timeout보다 짧다. 최초 중단은 timeout이
아니라 provider가 points를 비운 데 따른 정지다. 이후 reference age가 증가하는
것은 새 유효 제어점을 만들지 않았기 때문이며 계산 시간이 700ms였다는 뜻이 아니다.

이때 GPS 20행 모두 RTK FIXED(quality=4), heading=COG/융합, fix_age 최대 0.116초다.
이번 장애물 경로는 GPS 위치 대신 VehicleVector를 사용하므로 GPS 소실을 직접 원인으로
보는 근거가 없다. 생성 시점 자체의 planning_ms는 5초 주기 로그에 찍히지 않아
해당 계산의 정확한 실행시간을 주장하지 않는다.

실제 str_ref/str 변화는 존재한다. 경로 유효 구간 str_ref는 약 -0.056~0.061rad,
str은 -0.040~0.066rad였다. 이것만으로 물리 조향의 충분성이나 CAN 프레임 전체를
검증할 수는 없다. 확실히 검증한 것은 MGM에 경로 추종점·곡률이 전달됐다는 사실이다.

## 우선 수정 대상

1. x/y와 yaw를 동일 좌표계로 쓰기 전에 실제 필드 의미를 검증하고, 일관된 이동량으로
   검출 프레임과 현재 프레임을 변환한다. GPS를 사용할 경우에도 C의 정의는 검출 당시
   (장애물 x+2.7,0)로 유지 가능하다. 속도·헤딩 적분 대안도 실측 검증이 필요하다.
2. Zone 진입 시 제어점 공급이 준비되기 전 0명령이 나가고, 이후 0부터 가속하는
   전이 순서를 검토한다. 빈 경로 검사나 충돌 검사를 제거해서 해결할 문제는 아니다.
3. 최초 경로 탈락 때 사용한 scan, pose, 경로와 충돌 위치를 함께 기록해 정확한
   충돌 판정 원인을 오프라인 재현한다.
