# 최근 주행 재출발 실패 재검토

대상: `drive_logs/v2_20260914_063951_118844`, 2026-09-14 06:39:51~06:42:54 KST.
현재 저장소 drive_logs와 FMA_ws/drive_logs 확인 결과 가장 최근 기록된 실차 세션이다.
이후 빌드·HTML 테스트 로그는 실차 주행으로 취급하지 않았다.
기존 v28 스냅샷 해독/당시 파라미터 재생 18,310틱을 사용하고, 원본 transitions.csv
42행의 공통 필드 630개를 재대조해 모두 일치함을 확인했다. 현재 제어 코드로 과거
주행 결과를 대체하지 않았다. 이번 작업에서는 제어 코드/실행 중 프로세스를 변경하지 않았다.

  이때 external_stop=0, traffic_fail_safe=0, auto_estop=0, lidar_valid=1, gps_valid=1.

총 **85.350초** 비어 있었다. 검출이 사라진 순간에도 미완료 회피 상태가 유지되어,
차선/GPS 정상 주행으로 즉시 넘어가지 못했다.

플래너 원본 로그에는 `no collision-free cubic path with waypoint return at +2m` 이후
`obstacle cleared; cubic GPS return`이 기록됐다. 재계획은 계속 수행됐으므로
정지 상태가 플래너 실행 자체를 멈춘 것은 아니다. 원시 scan·후보별 탈락 원인이 없어
목표 후보 부족/충돌/곡률/복귀 구간 중 정확히 무엇이 실패했는지는 확정할 수 없다.
당시 최초/최근 장애물 관측 기억도 검사에 포함됐다.

주의: 명령 회복 직전 06:41:56.526에 측정 속도는 약 1.054m/s이고 MGM v_ref는 0이다.
56.536을 차량의 자율 재출발 시각으로 단정하지 않는다. 수동 이동/다른 제어 원인은
해당 로그만으로 구분할 수 없다. 그래프에서는 속도 피드백이 stale이면 공백으로 표시했다.

**USB 허브 연결 해제 → CAN 단절 → 지속 고장 래치**가 최종 정지의 시작 및 지속 원인이다.
카메라도 같은 사건 후 별도의 고장 래치가 남아 당시 재출발을 추가로 차단했다.
CAN 래치는 정상 링크로 돌아오는 것만으로 해제되지 않고 `/operator/go` 재인가에서
해제하도록 구현되어 있다. 해당 구간에는 래치 해제 로그가 없다.
카메라 고장 래치는 당시 노드 재시작을 요구했고 프레임 복구/초록불만으로 해제되지 않았다.
초록불을 다시 인식해도 외부/CAN 래치를 지우지 않는다.

커널 로그로 허브와 하위 장치의 연결 해제는 확인했다. 케이블 접촉, 허브 전원,
수동 분리 또는 다른 전기적 원인 중 어떤 것이 최초 원인인지는 확정할 수 없다.
이 구간 AUTO_ESTOP 진입으로 설명할 근거는 없으며 최종 정지 진입 당시 auto_estop=0이다.

## 현재 코드와의 차이

이 주행은 검출2m, 복귀2m, 과거 SAFE_STOP 정책으로 실행됐다(avoid 시작 로그 확인).
현재 검출3.5m/복귀2.7m/면 기반 후보·방향 안정화/센서 전체 상실 시 SAFE_STOP 변경 이전이다.
현재의 목표점 안정화가 이미 적용된 실차 결과가 아니며, 변경으로 이 주행 문제가
해결됐다는 증거로 사용할 수 없다.

현재도 유효 회피 제어점이 없으면 reference_motion_blocked로 명령을 보류하고,
CAN 고장 래치는 별도로 유지된다. 센서 전체 상실 SAFE_STOP 정책만 바꿔도 USB 단절이나
CAN 재인가 문제는 해결되지 않는다. 현재의 단일 카메라 고장과 당시 SAFE_STOP 이유32도
구분해야 한다. 우선순위는 USB 허브 단절 원인 확인과 CAN/카메라 복구 정책의 분리 검토,
회피 후보별 실패 사유 기록 및 새 플래너의 동일 환경 검증이다.
