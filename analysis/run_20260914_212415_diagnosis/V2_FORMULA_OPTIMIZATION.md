# v2_main 계산식 보존 최적화 검토

대상 HEAD 39db830, 비교용 origin/main 34fbfc0. 운영 코드는 수정하지 않았고 이 폴더에서만 오프라인 시제품을 작성했다.

사용자 요구: v2_main의 GPS station+1m anchor → 장애물 옆 목표점 → 목표점 투영 station+2.7m 복귀점의 cubic Hermite 계산식을 유지한다. main의 반응형 목표점 생성기로 교체하는 제안이 아니다.

현재 cubic_connector는 샘플마다 h(t), h'(t), h''(t), 좌표 튜플과 generator를 만들고 6회 sum을 수행한다. 합성 두 장애물 장면의 cProfile에서 곡선 생성 누적 시간이 콜백 시간 약 65%였다. 이 비율은 실제 주행 scan을 재생한 값이 아니다.

## 검증한 방법

fast_cubic_prototype.py:

1. 샘플 수 count가 같으면 동일한 t와 Hermite 기저계수를 재사용한다. count 키의 LRU 캐시 최대 128개. 지도/장애물/경로 자체는 캐시하지 않는다.
2. 곡선 시작·끝과 접선으로 구성되는 좌표 튜플은 곡선마다 한 번만 만든다.
3. 4항 내적의 generator와 sum 호출을 같은 덧셈 순서의 스칼라 식으로 바꾼다. 기존 sum의 초기 0 덧셈도 유지했다.

Hermite 계수, 접선 scale 1/1.25/1.5/1.75, spacing 0.05m, 샘플 수 공식, 곡률식, 특이점 판정, 경로 후보 순서, 최소 회전반경, 차체 충돌 검사와 복귀점은 동일하다.

benchmark_fast_cubic.py로 기준 구현과 시제품을 비교했다. 258개 곡선 입력(고정 seed 난수 250개+좌우/scale 조합 8개), 실제 생성 27,822개 점의 x/y/yaw/curvature가 float64 비트 단위로 일치했다. 이 검증이 모든 가능한 입력의 보편적 동치 증명은 아니다. 세 합성 장면에서는 전체 경로, 목표점, 실패 사유도 동일했다.

| 합성 장면 | 기존 콜백 중앙값 | 시제품 중앙값 | 속도비 |
| --- | --- | --- | --- |
| 범퍼 앞 3.3m 물체 | 21.25ms | 12.95ms | 1.64배 |
| 범퍼 앞 2.0m 물체 | 24.45ms | 14.38ms | 1.70배 |
| 범퍼 앞 0.7m 물체, 후보 실패 | 235.31ms | 139.42ms | 1.69배 |

각 값은 첫 실행 제외 6회 중앙값. 최초 캐시가 빈 실행도 각각 14.97/17.03/155.67ms로 측정했다. 수치 원본은 fast_cubic_results.json. ROS와 작업공간 환경을 source한 후 PYTHONPATH에 src/stack_avoid와 src/stack_avoid/test를 추가해 benchmark_fast_cubic.py를 실행한다. ROS 노드/실행기/하드웨어는 생성하지 않고 기존 시험 fixture에서 생산 콜백을 직접 호출한다.

## 추가 후보 — 아직 속도/동치 검증 전

- 한 scan 안에서 모든 후보가 공유하는 장애물 edge 배열을 한 번만 생성한다. 현 footprint_clear는 곡선 검사마다 surfaces를 순회해 NumPy 배열로 변환한다.
- _behind_surface의 빔 각도, 유효 거리와 관련 삼각함수 결과를 scan당 한 번만 계산한다. 후보별로 동일한 scan을 다시 파싱하는 비용을 줄인다.
- 좌표 변환용 cos/sin 및 장애물 변환도 동일 pose/scan 내에서 공유할 수 있다. 장애물 기억의 갱신 의미와 검사 순서를 유지해야 한다.
- 더 큰 개선이 필요하면 이 순수 계산 부분을 C++로 옮겨 동일 샘플/조건을 검사한다. 컴파일러 부동소수점 최적화로 경계 판정이 바뀌지 않도록 fast-math 등을 피하고 결과 동치를 검증해야 한다. 속도비는 아직 측정하지 않았다.
- 계산과 감지 메시지 발행을 분리하면 긴 계산 때문에 감지까지 멎는 현상을 줄일 수 있다. 이것은 식 자체의 가속과 별개인 실행 구조 변경이다. 오래된 scan/pose로 계산한 경로를 최신인 것처럼 발행해서는 안 된다.

이번 시제품만으로 실제 주행의 2.27~3.55초 지연이 해소됐다고 말할 수 없다. 원시 LiDAR scan이 보존되지 않아 현장 장면 재생이 불가능했고, 0.7m 실패 합성 장면도 아직 100ms를 넘는다. 후보 감소/간격 확대/충돌 생략으로 시간을 줄이지 않고 위 중복 계산부터 제거하는 것이 검증된 첫 단계다.

## 앞선 전체 점검 및 main 비교

- main은 gap 목표점 1개를 생성한다. 같은 181빔 합성 입력의 콜백은 약 0.30~0.34ms, v2는 성공 장면 약 22~41ms, 가까운 실패 장면 약 208~255ms. 두 방식의 기하 보장과 계산량은 서로 다르다. main이 목표점을 낸다는 사실만으로 그 장면의 안전한 통과를 입증하지는 않는다.
- main MGM의 단일 목표점 확장은 첫 점 (x/20,y/20), yaw=atan2(y,x), curvature=0을 만든다. v2는 목표점 원래 거리와 곡선 yaw/curvature를 유지한다. 브리지 두 파일은 main과 HEAD 사이에 변경 없음. 따라서 좌우 반전 외에 제어점 거리·방향·곡률 계약이 달라졌다. 실제 dSPACE 모델 없이 이를 물리 조향 응답까지 확정할 수 없다.
- 저장소 기본값 main v_base=1.0/v_avoid=0.6, v2는 2.0/2.0이다. 과거 성공 주행의 실제 실행 인자까지 확보한 비교는 아니다.
- main은 AVOID에서 TTC<1.3s로 정지할 수 있고 현재 v2는 독립 estop 입력을 사용한다. v2의 avoidable/TTC 표시는 동일한 정지 조건이 아니다.
- 현재 앞 LiDAR 설정은 raw forward +87도, estop yaw -87도로 수학적으로 일치한다. 실제 장착 방향은 원시 scan/현장 기준물 없이는 확정할 수 없다.
- 21:24 로그의 정지 명령 이후 2.21초/2.456m 추가 진행과 후진 종료 후 무효 회피 경로 대기는 앞선 보고서에서 재현했다. CAN 통신 누계는 지속됐지만 실제 브레이크 명령/제어기 내부 로그는 없다.

검증 범위: 기존 생산 코드 대상 Python 87개 및 MGM CTest 5개 통과. 시제품을 cubic_connector에만 대입한 추가 Python 결과는 최종 응답에 기재한다. 테스트 통과는 실차 성능 인증이 아니다.
