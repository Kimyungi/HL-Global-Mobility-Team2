# E-stop 직전 회피 미실시 추가 확인

대상: 2026-09-14 05:17 주행, 두 번째 장애물 검출부터 E-stop까지.

## 직접 원인 — 기록으로 확인

05:19:01.434(tick 11719)에 장애물을 검출했지만, 회피 경로가 0점이어서 `avoidable=false`였고 MGM은 AVOID에 진입하지 않았다. 그 후 05:19:03.224(tick 11898) E-stop까지 1.78995초 동안 차선 경로와 v_ref=1m/s를 유지했다. CAN 속도 적분 이동량은 약 1.779m다.

덤프에 기록된 파라미터와 해당 구간 179틱 전체를 추가 디코딩해 확인했다.

| 진입 관련 조건 | 당시 값 | 판단 |
|---|---|---|
| avoidance_enabled | 1 | 회피 기능 활성 |
| avoid_zone_only | 0 | 회피 구역 제한 없음. gps_avoid_zone=0은 차단 원인이 아님 |
| top | AUTONOMOUS_DRIVE | 주행 인가 상태 |
| mission | MISSION_IDLE | 당시 주차 미션이 회피를 차단한 것은 아님 |
| lidar_valid | 1 | 입력 단절 아님 |
| gps_valid | 1 | GPS 손실에 따른 제한 아님 |
| obstacle_detected | 1 | 장애물은 검출함 |
| 최초 TTC | 2.929초 | stack_avoid의 1.5초 기준 충족 |
| avoid_path.n | 0 | 회피 목표 없음 |
| avoidable | 0 | **진입 조건에서 탈락한 항목** |
| narrow_gap | 1 | 코드상 '장애물 검출 AND 목표 없음'; 실제 통로 폭이 좁다는 확정 측정은 아님 |
| auto_estop / external_stop | 0 / 0 | 이 시점에는 정지 입력도 없음 |

E-stop 전 새 회피 메시지가 18회 수신됐다. 그중 앞의 15회는 TTC가 1.5초 이상이었지만 모두 목표 0점이었다. 최초 검출부터 TTC 부족이었던 것은 아니다.

`stack_avoid/node.py`는 `avoidable = bool(msg.points) and msg.ttc >= self.ttc_stop`로 판단한다. `core/manager_step.cpp:234`는 일반 회피 진입에 `obstacle_detected && avoidable`을 요구한다. 회피 미진입 상태에서는 기존 차선 경로가 유효하므로 그 경로를 계속 선택한다. `manager_step.cpp:364`의 별도 TTC 정지도 회피가 이미 활성화된 경우에만 적용된다. 따라서 이번 입력에서는 앞서 빈 회피 경로를 이유로 회피/정지로 전환하지 않고, 별도 전방 E-stop이 발동할 때까지 차선 주행이 이어졌다.

**E-stop 직전 조향 미실시는 회피 명령을 액추에이터가 못 따른 상황이 아니라, 통합 로직이 회피 경로를 선택하지 않은 상황이다.**

## 빈 경로의 원인 — 추가 기하 재현

마지막 목표점과 GPS 이동량이 기존 경로 이탈 제한에 걸리는 패턴과 맞아떨어진다.

- 마지막 유효 회피 목표: 05:18:37.844, x=0.85945m, y=-0.89840m, yaw=-0.171277rad, curvature=0.
- 플래너 preview는 경로 길이 기준 1m다. 마지막 preview 구간을 직선으로 가정하면 현재 station 점은 목표점에서 해당 접선 방향으로 1m 뒤다.
- 이때 차량과 station 간 거리는 약 **0.73877m**다.
- 다음 GPS 이동량은 ENU에서 (-0.05903m, -0.11132m). 마지막 GPS 발행 헤딩 -124.2°를 이용하면 같은 직선 경로에 대한 다음 위치의 거리는 약 **0.77366m**다.
- 실제 목표점이 처음 0개가 된 시각도 바로 다음 05:18:37.944다.
- `stack_avoid/path_planner.py:71`은 station과 차량 거리가 **0.75m 초과면 새 경로 계획 전에 바로 None을 반환**한다.

`reproduce_station_loss.py`는 위 마지막 목표와 이동량으로 직선 경로를 구성한 뒤 실제 AvoidPathPlanner를 호출했다.

| 오프라인 조건 | 결과 |
|---|---|
| 마지막 유효 위치, 기존 경로 유지 | 거리 0.73877m, 목표 생성 |
| 다음 GPS 위치, 기존 경로 유지 | 거리 0.77366m, `vehicle outside bounded station neighborhood`, 목표 없음 |
| 같은 위치에서 새 장애물 검출 | 같은 검사에서 반환, 목표 없음 |
| 기존 경로 reset 후 같은 위치·장애물 검출 입력 | 빈 장애물 표면을 사용한 대조 환경에서 목표 생성 |

이 결과는 **기존 경로 이탈 검사가 새 장애물 회피 재계획을 막는 코드 경로**를 재현한다. 이전 회피는 완료 신호 없이 주차 미션으로 중단됐고, 플래너에는 미션 전환에 따른 경로 초기화가 없다. 새 장애물 검출 시 reset 역시 `_completed=true`일 때만 실행되는데, 이번 기록에서는 maneuver_done이 계속 false였다.

단, 이는 마지막 구간이 직선이라는 가정과 빈 장애물 표면을 사용한 기하 재현이다. 당시 전체 경로, 원시 스캔, 플래너 reason은 저장되지 않았다. 따라서 실제 실패 분기를 완전히 재생한 것은 아니며, **0.75m 이탈 제한이 유력한 원인**이라는 수준이다. reset 후 실제 현장의 장애물을 피할 유효 경로가 반드시 존재했다는 의미도 아니다.

## 수정 검토 지점

1. 중단된 회피의 기존 경로가 현재 차량 위치와 맞지 않을 때, 현재 스캔으로 안전성을 검증한 새 회피 경로를 생성할 수 있도록 경로 수명 관리를 정리해야 한다.
2. `장애물 있음 + 회피 경로 없음` 상태에서 기존 차선 주행이 그대로 유지되는 정책을 별도로 다뤄야 한다. avoidable을 강제로 true로 만드는 것으로는 유효한 조향 목표가 생기지 않는다.
3. 실패 사유, 경로 station과 이탈 거리, 위치 소스 등을 기록해야 같은 문제의 원인을 다음 로그에서 확정할 수 있다.

이번 작업은 진단 및 오프라인 재현만 수행했다. 차량 명령과 제어 코드는 변경하지 않았다.
